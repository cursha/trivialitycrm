# Module Seven Delivery Report

Data Quality, Duplicate Management, Record Merging, and Enrichment History — implemented on branch `module-seven-data-quality`, following the approved plan (`reactive-questing-spring.md`) presented and confirmed before any code was written. **Nothing has been committed, pushed, merged, or deployed.** Modules One through Six remain untouched in substance — every change to their existing files is additive or a targeted fix required for Module Seven's own correctness (enumerated below), never a rewrite.

## Starting point

Modules One through Six (CRM foundation, AI-assisted lead discovery, production hardening, Sales Workspace, Reporting, Communications) were complete, tested, and merged into `main` before this module started. Over six modules, three write paths (manual entry, AI-research transfer, spreadsheet import) had been creating and editing `Company`/`Contact` records with no way to find or fix duplicates or missing data in bulk, and the app had no generic audit log and no concept of merging two records. Module Seven adds all of this as a dedicated, permission-gated workspace (`/data-quality`) built entirely on the plan's three explicit reuse commitments: extend Module One's duplicate-matching service rather than compete with it, follow `run-search.ts`'s exact restart-safe worker idiom, and implement the enrichment provider as the third instance of the `types.ts` → `mock.ts` → `factory.ts` pattern already used twice.

## Features delivered

- **Data Quality Dashboard** (`/data-quality`, `view_data_quality`): counts of possible duplicate companies/contacts, missing address/phone/email/URL, invalid/suspicious emails/phones/URLs, records requiring manual review, and recently-resolved issues (7-day window) — each linking to a pre-filtered issue or duplicate list. Reflects the most recently *completed* scan, not a live query, with a visible "last scanned at" timestamp — the same async/job-based model AI research already uses, not a new one.
- **Table-driven data-quality rules** (`/data-quality/rules`, `manage_data_quality_rules`): `REQUIRED_FIELD`, `INVALID_EMAIL_FORMAT`, `INVALID_PHONE_FORMAT`, `INVALID_URL_FORMAT`, `DUPLICATE_EXACT_MATCH`, `DUPLICATE_NORMALIZED_MATCH`, `DUPLICATE_FUZZY_MATCH`, `STALE_RECORD`, `CUSTOM_REVIEW_FLAG` — each with entity type, field, severity, enable/disable, reorder (per entity type), and archive (never hard-deleted; `archivedAt` nullable timestamp, same convention as `SavedView`). `config` (a rule-type-specific JSON shape, e.g. `{ minSimilarity }` for fuzzy match or `{ staleDays }` for stale-record) is validated by a Zod discriminated schema (`src/lib/data-quality/rules.ts`) on every save, never trusted raw. 16 sensible defaults are seeded idempotently (`prisma/seed.ts`'s `seedDataQualityRules()`, matching the file's existing upsert-by-natural-key convention).
- **Normalization** (`src/lib/data-quality/normalize.ts`): US-state/Canadian-province, ZIP/Canadian-postal-code, city, and person-name normalization — a **new, separate** module from `src/lib/duplicates/normalize.ts`, reusing its `normalizePhone`/`normalizeEmail`/`normalizeAddressLine` directly rather than re-implementing them. Original display values (`Company.region`, `postalCode`, etc.) are never overwritten; only new `normalized*` columns are populated, at write time going forward and self-healed by the first scan for pre-existing rows (no fragile SQL backfill migration).
- **Duplicate detection**: extends, never competes with, `src/lib/duplicates/match.ts`'s `findPotentialDuplicates()`. A manually-triggered (`run_duplicate_scan`), rate-limited, restart-safe worker scan (`data-quality-scan` queue) scores every candidate company/contact pair 0–100 (`src/lib/data-quality/company-match.ts` / `contact-match.ts`) with human-readable reasons, matched/conflicting fields, and a confidence level (reusing the existing `ConfidenceLevel` enum). Exact/normalized matches use cheap grouped-key comparison; fuzzy matching is blocked by city+region (companies) or company (contacts) for tractability, using a hand-rolled Levenshtein similarity ratio (`src/lib/data-quality/similarity.ts`, zero new dependencies, confirmed with the user). **A fuzzy-only match is structurally capped at LOW confidence** — it can never by itself reach a "strong signal" HIGH/MEDIUM result, satisfying "fuzzy name similarity alone must not automatically merge anything."
- **Duplicate review queue** (`/data-quality/duplicates`, `review_data_quality`): filterable by entity type/confidence/status, each pair showing score/confidence/reasons. Opening a pair shows a full side-by-side comparison (`/data-quality/duplicates/[id]`, stacks on narrow screens via `grid-cols-1 md:grid-cols-2`). Actions: add a review note, mark "Not a duplicate" (snapshots the matched fields' current values; a later scan reconsiders — flips back to `PENDING` — only if one of those fields has since meaningfully changed, otherwise the pair is never re-suggested), defer, confirm, or begin a merge.
- **Safe company merge** (`src/lib/data-quality/merge-company.ts`, `merge_companies`): one transaction reassigns `Contact`, `CompanySource`, `EvidenceRecord`, `HistoricalScoreRecord`, `Activity`, `Task`, `PipelineStageHistory`, `SearchResult`, `EmailMessage`, `Appointment`, and `SequenceEnrollment` (with a same-sequence dedup guard — see Deviations) from the losing company onto the survivor, applies the reviewer's per-field decisions, resolves EOS scoring as one whole-record choice (keep the survivor's current score, or adopt the merged company's), tombstones the loser (`status: MERGED`, `mergedIntoId`/`mergedAt`/`mergedById` — never deleted, never had its own historical fields cleared), and writes both a human-readable `Activity` (`COMPANY_MERGED`) and a structured `DataQualityAuditEvent` with full before/after snapshots. Repeated/circular merges are rejected (a company already `MERGED` can be neither a survivor nor a loser again). Old links to a merged company (`/companies/[id]`) redirect to its current survivor, resolving a possibly-chained `mergedIntoId` pointer.
- **Safe contact merge** (`src/lib/data-quality/merge-contact.ts`, `merge_contacts`): reassigns `EmailMessage`, `Appointment`, `ConsentRecord`, and `SequenceEnrollment`; requires both contacts to belong to the same company (cross-company duplicates are resolved by merging the companies first — see Deviations); resolves consent/suppression conflicts to the **always-most-restrictive value, no override** (confirmed with the user, matching Module Six's CASL-safe default-deny design — `src/lib/data-quality/consent-conflict.ts`, a small pure function).
- **Data-quality issue workflow** (`/data-quality/issues`, `review_data_quality`): `OPEN`/`DEFERRED`/`RESOLVED`/`IGNORED`/`REOPENED` lifecycle, severity, assignment, notes, filters (entity/field/rule type/status/severity), pagination, and links to the affected record. Bulk assign/defer/ignore is supported; merges and field corrections stay individually reviewed, never exposed via the bulk path.
- **Enrichment history and provenance** (`/data-quality/enrichment`, `review_enrichment`/`manage_enrichment_settings`): a provider-neutral framework (`src/lib/enrichment/providers/{types,mock,factory}.ts`, the third instance of this codebase's provider pattern) tracking entity/field/previous/suggested value, source, evidence, confidence, request id, and decision. **Only the mock provider is implemented** — no real third-party enrichment service is purchased, enabled, or called, and no live network calls are ever made. A suggestion never auto-applies; accepting one runs the exact same validated-write-plus-normalization-plus-rule-recheck path as a manual correction. A rejected suggestion is kept, never deleted, for audit. Consent/suppression fields (`emailPermitted`, `doNotContact`, etc.) are structurally excluded from the enrichable-field allowlist — they can only ever be changed through Module Six's `recordConsent()`.
- **Record correction** (from an issue or an accepted enrichment suggestion): shows current/suggested values, validates, requires confirmation, writes an audit entry, and immediately re-runs the specific rule that flagged the issue — auto-resolving it if the correction actually fixed the underlying condition, leaving it open (with an updated description) if not.

## Conflicts with existing architecture (surfaced before writing any code, resolved as follows)

1. **`Activity`/`Task` have no `contactId`** — company-scoped only. Contact merge preserves only what's actually contact-linked (`EmailMessage`, `SequenceEnrollment`, `Appointment`, `ConsentRecord`); Activity/Task stay on whichever company they already belong to.
2. **`computeNormalizedFields()` (Module One) is spread onto `SearchResult`** in the AI-research pipeline (`run-search.ts`). Extending its return shape would have silently broken that write with columns `SearchResult` doesn't have. Resolved with a wholly separate `computeAddressNormalizedFields()` — the original function and its 5 existing call sites are untouched.
3. **`SequenceEnrollment` has no DB-level unique constraint per (company/contact, sequence)** — only an app-level check in `enrollInSequence()`. A merge's reassignment could leave two active enrollments in the same sequence for the resulting record. Resolved: after reassignment, any sequence left with more than one ACTIVE/PAUSED enrollment has all but the most-recently-enrolled one transitioned to `CANCELLED` with `stopReason: "Superseded by company/contact merge."` — no new enum value needed.
4. **EOS-1.0 `HistoricalScoreRecord` is a cohesive 10-category snapshot**, not independently-editable fields — EOS handling in a company merge is one whole-record decision, not decomposed per-category. All history rows from both companies are preserved and reassigned either way.
5. **Contact had no `status`/archive concept at all before this module.** Added `ContactStatus: ACTIVE/MERGED`, mirroring `CompanyStatus`.
6. **Cross-company contact merge is unspecified** (which company should the merged contact end up on?). Resolved by requiring same-company for a contact merge; a cross-company duplicate is resolved by merging the companies first, which reassigns all contacts onto one company.

## Matching and scoring approach

Company and contact scoring (`src/lib/data-quality/company-match.ts` / `contact-match.ts`) are pure, unit-tested functions returning `{ score: 0-100, confidence: HIGH/MEDIUM/LOW, reasons, matchedFields, conflictingFields }`. Exact signals (email, phone, website domain, exact-normalized name/full-name, address+postal+country) dominate the score and are the only things that can produce a `HIGH` or `MEDIUM` confidence (`hasStrongSignal` gate); a fuzzy name/full-name similarity above the rule's configured threshold (default 85) contributes a small, scaled bonus but can never by itself lift confidence above `LOW`. The scan groups records by shared exact/normalized keys for the cheap `DUPLICATE_EXACT_MATCH`/`DUPLICATE_NORMALIZED_MATCH` rule types, and blocks by city+region (companies) or company (contacts) before pairwise-scoring for `DUPLICATE_FUZZY_MATCH` — a documented tractability choice, not an oversight: an unbounded whole-table pairwise comparison doesn't scale, so two companies with similar names in different cities are simply never compared.

## Merge safety approach

Both `mergeCompanies()` and `mergeContacts()` run inside exactly one `prisma.$transaction`, re-verify neither record is already `MERGED` (rejecting repeated/circular merges), reassign every relevant FK via `updateMany`, apply the caller's explicit per-field decisions, tombstone the loser without ever clearing or overwriting its historical field values, and write a full before/after `DataQualityAuditEvent`. There is no automatic or one-click merge path anywhere in the codebase — the UI (`/data-quality/duplicates/[id]`) always requires picking a survivor, resolving every genuinely conflicting field, and an explicit `window.confirm()` before the server action runs (the same confirmation idiom every other destructive action in this app already uses — no new modal primitive was introduced, consistent with the brand guide's existing UI vocabulary).

## Worker jobs

One new on-demand queue, `data-quality-scan`, registered in `worker/main.ts` exactly like `run-search`: singleton policy keyed per scan id, `boss.work(..., { localConcurrency: 1 }, handleDataQualityScanJob)`. **Manually triggered only — no recurring tick** (confirmed with the user), mirroring how AI research searches already work. `runDataQualityScan()` (`src/lib/data-quality/scan.ts`) never throws internally — it persists `FAILED`/`errorMessage` on the `DataQualityScan` row itself; the pg-boss handler wrapper (`worker/handlers/data-quality-scan.ts`) re-derives failure from that row afterward and only then throws, so the queue's own retry/backoff applies. The per-record issue-evaluation phase is cursor-paginated (`lastProcessedCompanyId`/`lastProcessedContactId`) and restart-safe — a crash resumes from the cursor rather than restarting, verified directly by an integration test. The duplicate-detection phase re-scans fully on every run, which is safe (not resumable via a cursor) because every write is an idempotent upsert — documented as such in the code rather than overclaiming a resumability the phase doesn't have. Cancellation reuses `LeadSearch`'s exact `providerJobId` + cooperative-poll idiom. Triggering a scan is rate-limited (one per user per 5 minutes via the existing `checkRateLimit`).

**A real bug was caught and fixed during the worker-startup verification step**: `scan.ts` initially carried `import "server-only"`, which throws under the worker's plain-tsx execution (it isn't Next's "react-server" bundler context) — the exact class of issue `src/lib/prisma.ts` and `src/lib/research/run-search.ts` already document and deliberately work around. Fixed by removing the import with the same explanatory comment those files use; confirmed by actually starting `npm run worker` and watching every handler (including `handleDataQualityScanJob`) load cleanly before it hit the same pre-existing local port-8080 conflict every prior module's report also notes (an already-running worker instance) — the same check performed and re-confirmed clean at the end of every module in this codebase.

## Remaining limitations / known gaps

- **Duplicate detection loads the full active company/contact table into memory** for the grouping/blocking phase, not paginated like the issue-evaluation phase — a deliberate scope decision (documented in code) appropriate at this app's expected single-team scale, worth revisiting if company/contact volume grows very large, matching the same "fine at this scale, worth revisiting" precedent Module Four's territory-matching design already set.
- **No automatic/scheduled recurring scan** — confirmed with the user as manual-trigger-only, matching how AI research searches already work. A future module could add a recurring tick using the exact same `reports-tick`/`sequence-tick` idiom this codebase already has three examples of.
- **Only the mock enrichment provider exists.** No real third-party service is integrated, purchased, or called — the interface (`src/lib/enrichment/providers/types.ts`) is the seam a future module fills in, the same structurally-honest-stub precedent Module Six's Gmail-inbound methods established. No environment variable was added to select a provider, since there's nothing real to select yet.
- **The enrichment request form takes a raw record id**, not a search-by-name picker — a real UI would want to trigger enrichment directly from a company/contact detail page or from an open issue; this session scoped the review UI itself as the priority and left that discoverability improvement for a follow-up rather than modifying the already-large, established company/contact detail pages further than the minimum required (the merge-redirect and normalization-on-write additions).
- **Duplicate review is pairwise, not n-way grouped** — three or more mutually-similar records surface as multiple separate reviewable pairs rather than one group, matching the existing `findPotentialDuplicates()` precedent and keeping the merge UI's "pick a survivor" model tractable.
- **`CUSTOM_REVIEW_FLAG` has no automated evaluation** — it exists in the schema and rule-type enum for completeness and as a manual-flag seam, but nothing currently creates an issue of this type automatically; a future addition could wire a "Flag for review" action into the company/contact detail pages.
- **A rule's `field` value is validated against an allowlist at evaluation time, not at rule-save time** — a rule saved with an unrecognized field name is silently never violated rather than rejected at creation. Defensive (never an unsafe dynamic property access) but could be tightened with a save-time check against the real Company/Contact column list.
